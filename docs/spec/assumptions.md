# Assumptions

Each assumption was challenged and then resolved. "Decided" means the user confirmed it during
spec planning. "Proposed – to be revisited" means it is a working default that needs data or a
later decision. "Open (cross-repo)" means another repository must act.

| ID | Assumption | Challenged because | Resolution | Impact / status |
| --- | --- | --- | --- | --- |
| A-01 | gate-warden is implemented in Rust | The brief names no language | The ecosystem is Rust first, and the repo tooling is Rust | Decided ([ADR-0001](../adr/ADR-0001-rust-stateless-service.md)) |
| A-02 | One stateless deployable service | Restart and duplicate handling without state is harder | Idempotency plus reconciliation make it safe | Decided ([ADR-0001](../adr/ADR-0001-rust-stateless-service.md)) |
| A-03 | At M1, events arrive by App webhook directly | queue-keeper is the system's ingress | The brief allows a direct webhook during M1. NATS is added in L2 | Decided ([ADR-0009](../adr/ADR-0009-event-intake-port.md)) |
| A-04 | The pilot repository is commit-gate | — | Stated by the roadmap (M1) | Decided |
| A-05 | Config is taken from the default-branch HEAD at evaluation time | The base SHA or a cached config could be argued for | The base can be stale or a non-default branch | Decided ([ADR-0002](../adr/ADR-0002-gate-config-from-default-branch.md)) |
| A-06 | All check output is untrusted | Pack tools are "ours" | PR code runs inside the checks and can influence their output | Decided ([security.md](security.md)) |
| A-07 | Only `success`, `failure` and `action_required` are used | `neutral` would be friendlier for infrastructure errors | `neutral` and `skipped` satisfy required checks, so they fail open | Decided ([ADR-0005](../adr/ADR-0005-one-check-run-per-gate.md)) |
| A-08 | No `merge_group` support at L1 | Merge queues are common | Not in the brief | Decided; after factory role complete unless needed earlier |
| A-09 | The L1 checks form **G6 Build**, published as `gate-warden / G6 Build` | The brief names no gate for L1 | The handbook lists these checks under G6 | Decided ([gates.md](gates.md)) |
| A-10 | `external_id` = `gw1:<sha>:<gate>:<harness_version>:<config_sha>`. This extends the brief's key (SHA, gate, harness version) with `config_sha` | The brief's key omits default-branch content | Checks read the default-branch tree (policy, trust roots). Without `config_sha`, a stale result could be reused after the rules change | **New, needs confirmation** ([ADR-0006](../adr/ADR-0006-idempotency-key-and-check-run-reuse.md)) |
| A-11 | G2 and G7 are "after factory role complete" | The handbook says every G-gate is run by gate-warden | Not in the brief's increments; the brief says to stay within the listed levels | Decided |
| A-12 | **G9 is owned and published by release-ratifier. gate-warden supplies the signed G1–G8 results as inputs** | The handbook says gate-warden is the only required-check source, and that every G-gate is run by gate-warden | The user chose option A. How G9 is enforced (a required check from a second App, or release-ratifier refusing to tag or publish) is decided in release-ratifier's spec. **Risk:** a second required-check App weakens the forge-proof property | **Open (cross-repo):** release-ratifier spec; handbook update ([ADR-0011](../adr/ADR-0011-g9-owned-by-release-ratifier.md)) |
| A-13 | Performance targets: p95 ≤ 30 s event → `in_progress`; p95 ≤ 60 s overhead; 4 concurrent runs per instance | No load data | Defaults to be measured on the pilot | **Proposed – to be revisited** after M1 ([constraints.md](constraints.md#performance-targets-proposed--to-be-revisited)) |
| A-14 | Writing baselines to `.factory/baseline/` is deferred to L2 | gate-warden is the only writer, but writing to the default branch needs a ruleset bypass or a PR | Not needed at L1. The mechanism needs its own ADR | **Proposed – to be revisited** at L2 (GW-REQ-117) |
| A-15 | Gate applicability comes from `applies_to` (branch globs plus changed paths) in default-branch config. At L2 the coverage rule applies | Branch names are factory-chosen and spoofable | The coverage rule stops gates being dodged. How non-applicable required checks are concluded is still open | Decided for L1; the L2 detail is open ([gates.md](gates.md#applicability)) |
| A-16 | sandbox-runner is reached through a sandbox port; the adapter follows its eventual interface | sandbox-runner's interface does not exist yet | A port isolates the dependency. A dev adapter is allowed for tests only | Decided. **Open (cross-repo):** sandbox-runner interface, workspace preparation, killing processes between checks |
| A-17 | Checks deliver results as JSON in `GATE_RESULT_FILE` | stdout is simpler | See [tradeoffs.md](tradeoffs.md) | Decided ([ADR-0003](../adr/ADR-0003-standard-gate-result-format.md)) |
| A-18 | Infrastructure errors give `failure` with category `infrastructure` after bounded retries | — | Fail safe | Decided |
| A-19 | Ruleset guidance plus a read-only audit; no `administration` permission | Automation is more reliable | Admin rights on a security-boundary App are too risky | Decided ([ADR-0010](../adr/ADR-0010-ruleset-guidance-and-audit.md)) |
| A-20 | Feedback is carried in the check-run output | — | No direct hand-offs; GitHub is the record | Decided ([ADR-0008](../adr/ADR-0008-feedback-in-check-run-output.md)) |
| A-21 | Fork and external-actor PRs are not evaluated (`action_required`) | Fork contributions would then never get a verdict | Running untrusted code from outsiders is refused system-wide | Decided |
| A-22 | Superseded runs complete as `failure`/`superseded` | `cancelled` is the GitHub idiom | Keeps the conclusion type closed at three variants | Decided |
| A-23 | L3 seeds = SHA-256(SHA, gate, harness version, check id) | "Fresh seed" property tests conflict with idempotency | Fresh per SHA, reproducible per key | Decided for L3 (GW-REQ-135) |
| A-24 | Authorised humans = GitHub team membership mapped per tier in default-branch configuration | — | Uses GitHub as the record | Decided for L2 (GW-REQ-113/114) |
| A-25 | Schemas live in `schemas/` at the repo root | — | They are consumed by tools, not only by readers | Decided |
| A-26 | The name "gate-warden" is kept | It is a working name (handbook open question 1) | Renaming changes check-run names and rulesets | Decided for now |
| A-27 | One microVM per gate run, checks sequential. PR code in a check can tamper with later in-VM outputs (for example forged JUnit for `inventory`) | Handbook anti-faking relies on inventory | Mitigated by check ordering, a fresh result path per check and killing processes between checks. Not fully closed at L1 | **New, open.** Candidate fix: phased VMs or out-of-VM result collection ([tradeoffs.md](tradeoffs.md#sandbox-granularity)) |
| A-28 | The workspace is prepared outside the microVM by gate-warden. The default-branch and harness trees are mounted read-only | Who prepares workspaces (gate-warden or sandbox-runner) is not defined | Keeps credentials out of the VM, whichever service does it | **Open (cross-repo):** sandbox-runner |
| A-29 | gate-warden reads `harness.version`, `harness.commit`, `harness.repository` and `discipline_pack` from the pin. Gate definitions are found at a harness-defined path (proposed `disciplines/<pack>/gates/*.yaml`) | The pin schema and harness layout belong to the harness (handbook open question 2) | Defined here as gate-warden's needs | **Open (cross-repo):** harness spec |
| A-30 | The software pack supplies the wrappers that turn cargo build/fmt/clippy/nextest output into gate results. agent-gate and oracle-guard emit gate results natively or through wrappers | gate-warden must not contain this logic | Belongs to the pack and the tool repositories | **Open (cross-repo):** harness, agent-gate, oracle-guard |
| A-31 | `thresholds` in a gate definition is rejected before L3 | Ignoring it would be simpler | Silently ignored thresholds would fail open | Decided |
| A-32 | AGENTS.md and `.tech-decisions.yml` are added at the repo root | Neither existed | Needed by the agent workflow | Decided |
| A-33 | When the configuration cannot be resolved, the failure is published on every gate check-run name previously published for the repository, and always on `gate-warden / G6 Build` at L1 | gate-warden cannot know the planned gates without a resolvable configuration | Fail closed on every check run a ruleset could require (GW-REQ-014) | **Open (L2):** generalise once more gates exist; decide together with A-15 ([edge-cases.md](edge-cases.md)) |
